Introduction
1.1
Purpose
1.1.1
Product Identification
Product Name: Secure IoT Gateway Simulation for Resource Sensing (SIGS-RS)
Release/Revision Number: Version 1.0.0
1.1.2
Product Scope
The Secure IoT Gateway Simulation for Resource Sensing is a backend network software engine
designed to model, ingest, and process telemetry data from a theoretical community sensor grid.
This Software Requirements Specification (SRS) covers the backend simulation engine and the
middleware security layer exclusively. The scope of the product detailed in this document includes:
•
Telemetry Ingestion & Simulation: The core engine responsible for simulating high-volume,
concurrent IoT packet streams representing community resource metrics (e.g., water, energy,
or air quality data).
•
The Anomalous Packet Inspector: A primary subsystem of the middleware layer. This doc-
ument covers the logic and thresholds for the sliding-window algorithm used to evaluate real-
time data rates and payload integrity, as well as the protocols for dropping spoofed or malicious
packets.
•
The Privacy Anonymizer: The secondary subsystem of the middleware layer. This document
defines the data-masking pipeline that intercepts verified packets and strips personally identi-
fiable information (PII)—specifically geolocation metadata—prior to database persistence.
Out of Scope: This SRS covers only the backend gateway simulation and middleware components.
It does not include requirements for physical IoT sensor hardware, firmware development, or the
frontend graphical user interface (GUI) used for end-user data visualization.

system ensures user safety by stripping personally identifiable geolocation metadata from the
sensing logs prior to database insertion.

Overall Description
2.1
Product Perspective
2.1.1
Product Context and Origin
The Secure IoT Gateway Simulation for Resource Sensing is a new, self-contained software prod-
uct acting as the foundational R&D testing environment for a broader, upcoming physical smart-
community grid. Rather than replacing an existing system, this simulation engine acts as a precursor
component to the larger enterprise physical gateway system. It allows developers to rigorously test
high-volume telemetry processing and the custom middleware security layer in a risk-free, simulated
environment before committing to expensive hardware deployments.
2.1.2
System Interfaces and Interconnections
Within the overarching enterprise architecture, this software serves as the intermediary routing and fil-
tering layer. It interfaces with an external virtual data generator (simulating the physical IoT commu-
nity sensors) via standard MQTT/HTTP protocols, and outputs sanitized telemetry logs to an external
persistent database. The internal architecture dictates that all ingested traffic must sequentially pass
through the middleware’s two primary security subsystems—the Anomalous Packet Inspector and
the Privacy Anonymizer—before reaching the database interface.

2.2
Product Functions
2.2.1
Major System Features and Functions
The Secure IoT Gateway Simulation for Resource Sensing operates primarily as a backend processing
and routing engine. The major functions the system performs can be summarized into the following
high-level capabilities:
•
Telemetry Ingestion: Receives and models high-volume, concurrent simulated packet streams
representing community resource metrics (e.g., water, energy, air quality).
•
Real-Time Threat Detection: Utilizes the Anomalous Packet Inspector to continuously
monitor incoming data rates and evaluate payload integrity against predefined baseline thresh-
olds.
•
Automated Threat Mitigation: Automatically drops spoofed or malicious packets that ex-
ceed the anomaly thresholds calculated by the internal sliding-window algorithm.
•
Data Sanitization: Routes verified packets through the Privacy Anonymizer pipeline to de-
tect and strip personally identifiable information (PII), specifically targeting sensitive geolo-
cation metadata.
•
Secure Data Persistence: Forwards the fully sanitized and verified community sensing logs
to the external persistent database for storage and future analysis.

2.4
Operating Environment
2.4.1
Operating Environment
The Secure IoT Gateway Simulation is a highly concurrent backend service designed to process high-
volume telemetry traffic. It is engineered to operate within modern, scalable server environments and
relies on containerization for consistent deployment.
2.4.1.1
Hardware Platform
The software does not run on physical IoT edge devices; instead, it requires robust backend infrastruc-
ture to simulate the heavy load of a community sensor grid.
•
Architecture: x86_64 or ARM64 multi-core server architectures.
•
Minimum Simulation Specs: A minimum of 16 vCPUs and 32 GB of RAM is recommended
to ensure the Anomalous Packet Inspector can compute the sliding-window algorithm across
thousands of concurrent connections without bottlenecking the ingestion pipeline.
2.4.1.2
Operating Systems
The system is built as a platform-agnostic, containerized application, but native deployment is offi-
cially supported and tested on Linux environments:
•
Primary OS: Ubuntu 22.04 LTS (or newer).
•
Secondary OS: CentOS Stream 9 or Alpine Linux (for lightweight container builds).
2.4.1.3
Software Ecosystem and Coexistence
The simulation engine acts as an intermediary node and must peacefully coexist and interface with
several external components and third-party software layers:
•
Container Orchestration: The engine runs within Docker containers and is designed to be
orchestrated by Kubernetes (K8s) for horizontal scaling during stress-testing scenarios.
•
Message Brokers: The ingestion layer must interface smoothly with standard IoT message
brokers, primarily MQTT (e.g., Eclipse Mosquitto or EMQX) and HTTP REST APIs, to re-
ceive data from the external virtual sensor grid.
•
Persistent Storage Engine: Once telemetry passes through the Privacy Anonymizer, the
output pipeline connects directly to time-series or relational databases, such as TimescaleDB,
InfluxDB, or PostgreSQL, to store the sanitized logs.
•
Virtual Data Generators: The system coexists alongside Python or Go-based load-generation
scripts that act as the simulated community sensor nodes, continuously pushing both legitimate
and malicious telemetry payloads into the network.

2.5
Design and Implementation Constraints
2.5.1
Design and Implementation Constraints
The development and architecture of the Secure IoT Gateway Simulation are bound by several strict
technical, regulatory, and operational constraints:
•
Regulatory and Compliance Mandates: The Privacy Anonymizer pipeline must strictly
adhere to the internal Data Anonymization and Privacy Compliance Guidelines (Version 3.0).
Because the system simulates real-world community sensing logs, the stripping of personally
identifiable geolocation metadata must be absolute to comply with enterprise data protection
standards modeling real-world regulations (e.g., GDPR, CCPA).
•
Algorithmic Performance Limits: The Anomalous Packet Inspector utilizes a stateful
sliding-window algorithm to track real-time telemetry rates. This imposes severe memory
and timing constraints. Developers must ensure the in-memory state tracking for thousands
of concurrent virtual sensors does not exceed the maximum 32 GB RAM allocation or delay
the ingestion pipeline by more than 15 milliseconds per packet.
•
Protocol Restrictions: Inbound communication interfaces are strictly limited to MQTT and
HTTP/HTTPS REST protocols to accurately mirror the eventual physical edge-device capa-
bilities. Proprietary or non-standard IoT protocols cannot be used for the external virtual data
generator interfaces.
•
Architectural Mandates: The software must be fully containerized (Docker) and orchestration-
ready (Kubernetes). Developers are constrained from using any OS-specific or hardware-
dependent libraries that would break the platform-agnostic, microservices-based deployment
model.
•
Database Interface Standards: The output pipeline must be written to interface exclusively
with the organization’s pre-approved standard for persistent storage (PostgreSQL/TimescaleDB).
The sanitized data schemas must perfectly match the existing upstream analytical database
tables.

Assumptions

algorithm. The software requires the hardware to provide standard x86_64 or ARM64 multi-

hardware-induced latency or unintended packet dropping.

4.
System Features
This section details the core functional requirements of the Secure IoT Gateway Simulation for Re-
source Sensing (SIGS-RS). To best reflect the system’s architectural pipeline and the sequential flow
of telemetry data, these functional requirements are logically organized by middleware subsystem.
The requirements are divided into the system’s three primary processing layers:
•
4.1 Telemetry Ingestion: The baseline capabilities for receiving, parsing, and queuing high-
volume concurrent payload streams from the virtual sensor grid.
•
4.2 Anomalous Packet Inspector: The sliding-window algorithms, baseline threshold met-
rics, and automated packet-dropping protocols used to identify and mitigate malicious traffic.
•
4.3 Privacy Anonymizer: The compliance and data-masking pipeline responsible for identi-
fying and stripping personally identifiable geolocation metadata prior to database persistence.
4.1
Telemetry Ingestion Pipeline
4.1.1
Description and Priority
This feature encompasses the core capability to securely receive, parse, and queue high-
volume concurrent telemetry streams (via MQTT and HTTP) generated by the external
virtual sensor grid. Priority: High. It is the foundational entry point for all data entering
the simulation engine; without it, downstream middleware testing cannot occur.
4.1.2
Stimulus/Response Sequences
Stimulus: The virtual sensor grid initiates a secure MQTT connection and transmits a
batch of JSON telemetry payloads.

4.2
Anomalous Packet Inspector
4.2.1
Description and Priority
The Anomalous Packet Inspector is the primary security middleware subsystem. It uti-
lizes an in-memory sliding-window algorithm to evaluate the frequency and integrity
of incoming telemetry payloads. Its purpose is to detect and mitigate spoofing attacks,
Denial of Service (DoS) attempts, and corrupted sensor data before it penetrates further
into the network. Priority: High.
4.2.2
Stimulus/Response Sequences
Stimulus: The ingestion pipeline forwards a queued telemetry packet to the Inspector.
Response: The algorithm calculates the current packet rate for the originating sensor
ID. If the rate and payload values fall within baseline thresholds, the packet is flagged
as ’Verified’ and forwarded to the Privacy Anonymizer.
Stimulus: A sensor exceeds the defined transmission rate (e.g., a burst of 100 packets
in one second) or submits statistically impossible resource metrics.
Response: The Inspector immediately drops the offending packet(s) from memory and
records a violation in the internal security log.

4.2.3
Functional Requirements
REQ-API-1:
The system shall maintain an in-memory state tracking the timestamp of

REQ-API-2:

REQ-API-5:

4.3
Privacy Anonymizer
4.3.1
Description and Priority
The Privacy Anonymizer is the secondary subsystem of the middleware layer. It func-
tions as a strict compliance and data-masking pipeline that intercepts verified telemetry
packets to detect and strip personally identifiable information (PII)—specifically sen-
sitive geolocation metadata—before the logs are persisted to the database. Priority:
High. Failure to strip this data violates enterprise privacy compliance guidelines.
4.3.2
Stimulus/Response Sequences
Stimulus: The Anomalous Packet Inspector forwards a ’Verified’ telemetry packet to
the Anonymizer pipeline.
Response:
The system parses the JSON payload, identifies restricted keys (e.g.,
latitude, longitude, mac_address), removes them, and forwards the sani-
tized payload to the database connection pool.
Stimulus: The system encounters a payload structured in an unrecognized format
where targeted PII keys cannot be safely isolated.
Response: The system defaults to a fail-secure state, dropping the entire packet to
prevent accidental PII leakage into persistent storage, and logging a schema compliance
error.

Performance Requirements
The performance of the Secure IoT Gateway Simulation (SIGS-RS) is critical. It must accurately
model the high-stress environment of a physical community sensor grid while performing real-time
security and privacy analysis. The system is designed to handle high concurrency with strict latency
boundaries to prevent ingestion backpressure.
REQ-PF-1:
Throughput Capacity: The simulation engine shall successfully ingest

connected virtual sensors.
REQ-PF-2:

Packet Inspector and Privacy Anonymizer) shall complete the validation, metadata stripping, and
database queuing for any individual packet in under 15 milliseconds.
REQ-PF-3:

window algorithm shall be memory-optimized to operate stably utilizing no more than 24 GB of
active RAM, ensuring safe overhead within the 32 GB minimum system environment to prevent
Out-Of-Memory (OOM) failures.
REQ-PF-4:
Horizontal Scalability: The containerized system shall be capable of
stateless scaling, triggering Kubernetes horizontal pod autoscaling (HPA) events when sustained CPU
utilization exceeds 75% for more than 2 minutes.

Safety Requirements

Appendix A: Glossary
•
MQTT (Message Queuing Telemetry Transport): A lightweight publish-subscribe messag-
ing protocol designed for constrained devices and low-bandwidth networks, acting as the pri-
mary ingestion protocol for the simulation.
•
PII (Personally Identifiable Information): Any data that could potentially identify a specific
individual. In the context of this system, it primarily refers to sensor geolocation metadata
(e.g., latitude, longitude, and MAC addresses).
•
SIGS-RS: Secure IoT Gateway Simulation for Resource Sensing (the system defined in this
SRS).
•
Sliding-Window Algorithm: A computational data structure used by the Anomalous Packet
Inspector to maintain a rolling subset of recent telemetry data. It evaluates real-time transmis-
sion rates over a fixed timeframe to detect anomalies without retaining long-term state.
•
Telemetry Payload: The JSON-formatted data packets containing simulated environmental
readings and sensor metrics.
